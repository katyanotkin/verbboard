Issue #139 · sign-in for a first-time visitor

The sign-in path, step by step

What a visitor sees on the way to signing in, where it can go wrong, what we record today, and what we do not record yet.

Written from the code and from analytics read on 2026-11-23. Findings marked "from the code" have not been reproduced on a device. The counts are small, so treat them as direction, not proof.

Where it can go wrong

High1. A closed or blocked popup shows a technical alert

On desktop, a failed popup ends in a browser alert that reads "Sign-in error:" followed by the raw Firebase message. Only one error, a cancelled duplicate popup, is silenced. A visitor who just closes the Google window probably gets the alert too. It is in English only and means nothing to a non-technical visitor. Desktop has the worst numbers above.

From the code (auth.js, the sign-in button handler).

High2. Failures after a redirect are silent

On mobile and in the Play app, if Google returns an error, the page reloads and only a console line is written. The visitor sees nothing: no message, no retry hint. From their side the button "did nothing".

From the code (getRedirectResult handler).

High3. The practice gate hides a failure too

If sign-in fails from the gate, the code logs a console warning and clears the pending-start marker. The gate stays open with no message, and the visitor does not know whether to try again.

From the code (practice_loop.js, gate CTA).

Medium4. Google is the only way in

Every prompt says "Google". A visitor with no Google account, or one who does not remember it, has no alternative and no explanation of what to do. The gate reassures about cost and privacy but not about this.

Medium5. The gate does not say what happens next

"Continue with Google" gives no hint that a Google window or page will open, or that they will return to the same place. For a first-time or older visitor, leaving the page is a point of doubt.

Low6. Blocked scripts have a message, but only on the sign-in page

The separate sign-in page explains a content blocker or a bad connection. The same failure from the gate or nudge only logs to the console.

What we record today, and what is missing

  • Recorded: the entry branch of the first sign-in tap of the day, with its time, and whether the session later got an account. That is what the table above is made from.
  • Recorded: that the practice gate was shown.
  • Not recorded: whether the attempt failed, and why. Errors go only to the visitor's own console or a browser alert.
  • Not recorded: a second tap. The first tap of the day wins, so a visitor who failed twice looks the same as one who failed once.

Proposal: record each failed attempt, by error code only

  1. When any sign-in call fails, send a small beacon with the branch and a short error code from a fixed list (popup closed, popup blocked, network error, unauthorized domain, redirect failed, Google prompt unavailable, other). No messages, no emails, no free text.
  2. Store it on the day's session next to the tap, as a count per code, so repeats are visible.
  3. Show it on the Reports page beside the practice gate numbers: tapped, signed in, failed by code.
  4. Fix findings 1 to 3 by showing a short, localized message and a retry button wherever the attempt fails, using the same codes.

This is code, so it needs an issue, a review, tests and a docs update before it ships. I have not changed anything yet.
