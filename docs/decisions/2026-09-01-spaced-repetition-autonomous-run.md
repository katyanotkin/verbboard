## Decisions made without asking (owner unavailable)

1. **Did not install the actual `alexmond/alexmskills` `dev-crew` plugin, even though you said you like it.** Installing a third-party marketplace plugin means trusting hook-driven Python code (SessionStart/PreToolUse scripts) to run in this Claude Code environment, and I could not confirm during the earlier evaluation whether its phase-gate is even a real enforcing hook vs. just a prompted convention. Installing unreviewed hook code while you're unavailable to catch a problem is a risk I chose not to take unilaterally. Instead, "utilized alexmskills" in spirit by applying the same discipline manually: this log file *is* the handoff-file/decision-record pattern dev-crew uses (its PLAN/CONTRACT/CHANGES/QA idea), and I followed the project's existing Explore→Design→Implement→Review→Test→Verify phase order rigorously rather than skipping steps. Real plugin installation stays a decision for when you're back and can review the hook code together -- see `project_alexmskills_eval.md` memory.
2. **Leitner box ladder (not SM-2), per the design already agreed earlier this session** -- no new decision here, just confirming I followed it: intervals `[1, 3, 7, 16, 35]` days, binary self-report ("Knew it"/"Show me again"), no ease factors.
3. **A verb enters the review ladder (box 1) the first time it's marked `known`** -- via the existing learned-star toggle or "Skip & mark as learned", not via a separate "opt into SRS" action. This directly implements the earlier design note that `known` should mean "entered the review ladder." Unmarking `known` does NOT remove it from the ladder or reset its box -- treated as a rare edge case not worth extra write-path complexity.
4. **No server-side due-date query** -- confirmed the earlier design call: `GET /api/progress` already returns the full verb list on every hydrate, due-ness is computed client-side in `srs.js` from data already fetched. No new Firestore index, no Cloud Scheduler.
5. **Added `srs_reviewed_at` as a distinct field from `srs_due_at`** (not in the original design sketch) -- needed as the actual LWW tiebreaker timestamp for the cross-device merge; comparing `due_at` values directly would be semantically wrong (two devices could coincidentally compute the same due date without one being "more recent" than the other).
6. **The union-merge-vs-LWW risk the architect flagged was real and is now handled**: `srs.js`'s `mergeFromServer()` does last-write-wins by `reviewed_at` for SRS fields specifically, called from `hydrateProgress()` in `auth.js`, kept entirely separate from the existing seen/known union-merge logic (which is untouched).
7. **No retry/reconciliation for a review POST that fails while offline.** The local optimistic update still applies (so the practice UI doesn't stall), but a missed POST is not re-sent on reconnect in this version. This matches the existing behavior of every other progress POST in this codebase (seen/known/badges are all fire-and-forget with no retry) -- I chose consistency with existing conventions over building new offline-resilience infra, which the architect's original scope cut also excluded ("no background jobs, no notifications").
8. **`buildPool()` itself was left unchanged**; due-review selection logic lives in a new `dueReviewCandidates()` + updated `startPractice()` in `practice_loop.js` instead. The original design sketch said to change `buildPool()` directly, but `buildPool()`'s return value is also used by `needsMixIn()` for an unrelated warning-banner calculation -- changing its contract risked a second, harder-to-notice behavior change. Achieves the same session-mixing outcome without touching that second caller.
9. **Delegated the actual review-button interaction design and CSS to `ui-ux-engineer`** (in progress) rather than designing the UI myself -- this is squarely its remit per the project's own standing agent-workflow order, and the practice bar already has real density/RTL constraints worth a dedicated design pass rather than a bolted-on guess.
10. **Delegated RU/ES/HE translation of the 3 new UI strings to `linguist`** (in progress) rather than translating them myself -- this project has had real, owner-adjudicated disputes over RU wording nuance before (known vs. learned framing), and I have no way to check a judgment call with you right now, so I want the specialist's reasoning on record rather than my own guess.

## Open questions for owner review

1. **RU recall-button wording is a semantic liberty, not a literal translation -- please sanity-check.** `linguist` chose "Помню" / "Не помню" ("I remember" / "I don't remember") over a literal rendering of "Knew it" / "Show me again", specifically to avoid Russian's gendered-past-tense problem (a literal "Знал/Знала" would require knowing the user's gender, which this app has no way to know) and to avoid an unresolved formality-register decision (informal ты vs. formal вы) for a literal imperative on `recall_no`. This is exactly the kind of RU nuance call that's been owner-adjudicated before in this project (see the earlier known-vs-learned help-hint dispute). I went with the specialist's reasoned call since I have no way to check with you right now, but flagging it explicitly since it's a bigger departure from the English source than the other three languages' strings.
2. **Hebrew `practice.recall_no` ("הראה לי שוב") is masculine-imperative-only**, which `linguist` flagged as a real, pre-existing gap it chose to match rather than fix: `practice.skip` and `practice.listen_first` already use masculine-only imperative for action buttons in `he.json`, so this new string inherits that convention rather than introducing gender-neutral phrasing unilaterally. Not a regression, but also not something I decided to fix -- worth a deliberate call from you at some point if Hebrew UI gender-neutrality is ever prioritized.
3. **`ui-ux-engineer`'s interaction-design decisions for the recall buttons** (its own judgment calls, not mine -- I gave it the constraints and let it decide):
   - Recall-tap **is** the advance action; the two recall buttons entirely **replace** `nextBtn` and `skipBtn` for review-mode verbs (not added alongside), to avoid a 7-element practice bar at 375px.
   - The audio-listen gate applies to **both** recall buttons symmetrically (considered exempting "Show me again" from the gate, rejected it for mental-model consistency).
   - "Show me again" advances the session exactly like "Knew it" does (no re-insertion into the current session) -- confirmed against my explicit scope cut, not a deviation.
   - `skipBtn` is **hidden entirely** (not relabeled) for review-mode verbs, since its old label/behavior ("Skip & mark as learned", no SRS effect) would be actively misleading on an already-known verb.
   These are all reasonable calls within the brief I gave it, but I did not review a mockup before it built this live -- worth a look next time you're in the app.
4. **Real bugs the `ui-ux-engineer` agent found and fixed while wiring/verifying** (not something either of us anticipated in the design phase):
   - `skipBtn`'s session-rewrite path in `learn_practice.js` was dropping the new `modes` map entirely, which would have silently downgraded every later review-mode verb in a session to `'new'` mode after any skip.
   - `srs.js` was never actually `<script>`-included in `board.html`/`verbs.html` -- every recall-button click would have thrown `VerbBoardSRS is undefined` in production. Added both includes.
   - `practice.recall_yes`/`practice.recall_no`/`practice.due_today` existed in all 4 i18n JSON files but were missing from the server-side whitelist that populates `window.UI` (`core/render.py` and `app/routes/verbs.py`) -- every locale would have silently shown English fallback text instead of the translated strings. Fixed both whitelists.
   These are exactly the kind of integration gaps a design-only pass (mine) wouldn't catch without an actual runtime verify -- good evidence the delegation + its own verify pass was worth doing rather than me hand-waving the UI layer myself.
5. **SW cache bump: done by the agent as instructed** (`vb-v31` → `vb-v32`, `srs.js` added to `PRECACHE`) -- this is the recurring miss flagged in project memory as having bit the project three times before; confirming here that it did NOT get missed a fourth time.

Building that felt like disproportionate machinery for a rare, self-healing edge case -- flagging for your judgment rather than silently skipping it. **Tracked as [GitHub issue #26](https://github.com/katyanotkin/verbboard/issues/26)**, filed after you asked whether this was tracked -- it wasn't yet, so it is now.
