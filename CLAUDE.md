# CLAUDE.md — VerbBoard Project Context

@AGENTS.md
@workflow.md

VerbBoard is a verb-focused language learning app: conjugation tables, real usage examples, audio, and practice loops. Unknown searches become demand signals that drive future verb coverage. FastAPI + server-rendered UI, GCP backend.

---

## Tech Stack

- **Backend:** Python 3.12 + FastAPI
- **Frontend:** Vanilla JS + CSS (no framework -- do not introduce one)
- **Data:** GCP Firestore (single source of truth in all environments)
- **Audio:** GCS-only (`AUDIO_BUCKET`); pluggable backend abstraction in `core/audio_backend/`
- **AI generation:** Anthropic Claude -- Haiku (`claude-haiku-4-5-20251001`) for English, Sonnet (`claude-sonnet-4-6`) for all others; GCP Gemini for translation workflows
- **Auth:** Firebase Auth (Google sign-in); server validates ID tokens on `/api/progress/*`
- **Secrets:** GCP Secret Manager (prod/stage) or `.env` (local)
- **Infrastructure:** GCP -- Cloud Run + Firestore + GCS
- **Cross-language search:** Vertex AI Gemini (`gemini-2.5-flash-lite`) translates EN query to target language lemma; `translate_search_query()` in `core/translation_service.py`
- **App entry point:** `app.main:app`

## Key Architectural Patterns

**Language plugins:** `core/languages/{lang}/plugin.py` self-registers on import (triggered in `app/main.py`). Each implements `build_board(verb, voice_key, voice_label) -> Board`.

**Firestore data model:**
- Verb collections: `verbs`, `verb_candidates`, `demand_signal`, `demand_signal_labels`
- Bookkeeping-only: `verb_pair_generation_attempts` -- one doc per (language, input lemma) that Claude either failed to generate or resolved to a different lemma than the lookup key, keyed by the *input* lemma's `verb_id` with an optional `resolved_verb_id` pointer; read by `core.verb_service.generate_and_promote_verb()` (Russian aspectual-pair generation, `core/languages/ru/plugin.py`) to skip a repeat Claude call within `_PAIR_ATTEMPT_RETRY_AFTER` (24h) instead of paying for one on every `/learn` render of a verb whose pair keeps missing. Never read as verb data.
- Bookkeeping-only: `verb_of_the_day` -- one doc per (language, date) (`{language, date, verb_id}`), doc id `{language}_{date}`, written once via `create()` on the first request of the day and read on every request thereafter by `core.verb_loader.get_verb_of_the_day()`. See the Verb of the Day pattern entry below for why this exists.
- Doc ID: `{language}_{transliterated_lemma}` (e.g. `en_go`, `ru_idti`) -- Cyrillic/Hebrew transliterated to ASCII
- Key fields: `language`, `verb_id`, `lemma`, `rank`, `forms`, `examples`, `search_extract` (array), `morph`, `display_lemma`, `display_forms`
- Search: `find_verb_by_search_extract()` uses `array_contains` on normalized query
- User progress: `user_progress/{uid}/languages/{lang}/verbs/{verb_id}` -- `seen`, `known`, timestamps
- User practice: `user_practice/{uid}/languages/{lang}` -- `badges` (list of ints), `started_at`, `updated_at`
- Legacy fallback: old data at `user_progress/{uid}/verbs/{verb_id}` is read if new path is empty
- Security rules and composite indexes are tracked in source control (`firestore.rules`, `firestore.indexes.json`, both referenced from `firebase.json`'s `firestore` block) as of 2026-09-16 (issue #39) -- previously these existed only as manual console state with no way to recover them from git. `firestore.rules` is a verified byte-for-byte copy of the live deny-all ruleset (`allow read, write: if false` for all documents -- the app works only because the server exclusively uses the Admin SDK, which bypasses rules); `firestore.indexes.json` holds the 3 composite indexes that actually exist in the live project (pulled via `gcloud firestore indexes composite list`, not hand-derived from reading query code -- Firestore's automatic single-field indexing covers equality-only and equality+array-contains query combinations without an explicit composite index, so most `.where().where()` chains in this codebase, including the primary search path's `language ==` + `search_extract array-contains`, don't actually need one; a composite index is only required here for an equality filter combined with `order_by` on a different field, which is the one index that exists, for `list_verbs_recent()`). **Neither file is wired into the deploy pipeline yet** -- committing them is source-of-truth recovery only; `firebase deploy --only firestore` is deliberately not yet added to `cloudbuild.stage.yaml`/`Makefile` since that changes what happens on every future push (see the tracked follow-up issue). Drift detection exists instead as the read-only `tools/check_firestore_drift.py` (`make firestore-drift`): it compares the live ruleset and composite indexes against the committed files and exits 1 on any difference (checked clean on 2026-09-25); auto-deploying them remains an owner-sign-off decision tracked in #51.

**Demand-driven generation pipeline:** Unknown searches are logged as demand signals. Admin flow: review signals -> generate structured verb data via Claude + Gemini -> preview candidate on live `/learn` page -> promote to `verbs`. Admin triggers `_call_claude(language, query)` in `admin_candidates.py` (async) -> strict JSON -> stored as candidate. All AI config lives in `core/settings_ai.py`. Per-language system prompt via `get_cached_system(language)` with `cache_control: ephemeral`. Hebrew gets `max_tokens=4096`, others 2048. `promote_candidate`/`regenerate_verb`/`regen_verb_examples`/`regen_verb_forms` in `admin_candidates.py` all call `invalidate_entries_cache(language)` after writing the live `verbs` doc, so a promote/regen doesn't leave `/verbs`/`/learn` serving a stale cached list for up to `load_entries_for_language`'s 300s TTL.

**On-the-spot autogen abuse guard (EN/ES/IT/FR/RU search-miss path, and RU pair completion):** both `/search_verb_by_lang` and `/search_verb` (`app/routes/home.py`) are public, unauthenticated GET routes that can trigger a paid generation + auto-publish to live `verbs` when a search misses (`core.verb_autogen.autogenerate_missing_verb`). Generation is provider-dispatched per language (`core.verb_autogen._generate_verb_payload`): Gemini for EN/ES/IT/FR, Claude/Sonnet for Russian (`_CLAUDE_AUTOGEN_LANGUAGES`) -- matching this project's Sonnet-for-non-English convention rather than adding RU to the Gemini path. Russian's cold generation (no anchor verb, unlike pair completion below) goes through an extra `core.languages.ru.validation.validate_ru_payload()` gate before any live write -- checks aspect/tense-slot consistency and pair-field sanity; a failure writes a `verb_candidates` doc with `status="needs_review"` instead of publishing. `autogen_rate_limited(client_ip)` (`core/verb_autogen.py`, backed by `core/rate_limit.py`'s `SlidingWindowRateLimiter`) caps this at 5 triggers/10min per client IP, in-process/per-Cloud-Run-instance -- a soft, best-effort cap, not a hard security boundary, since Cloud Run can run multiple instances, shared across all languages/providers regardless of per-call cost. `_client_ip()` in `home.py` deliberately reads the *last* `X-Forwarded-For` hop (the one appended by infra closest to Cloud Run), not the first (client-supplied and spoofable) -- opposite of `core.analytics.session_tracker`'s fingerprint, which uses the first hop for best-effort analytics where spoofability doesn't matter. `build_storage_verb_id`'s Cyrillic transliteration can collide distinct lemmas (e.g. "сесть"/"съесть" both -> "ru_sest"); `_allocate_verb_id()`/`_allocate_candidate_doc_id()` fall through to a numbered suffix on a lemma/query mismatch rather than silently treating the collision as "already generated." Russian's separate, already-live pair-completion path (`core/languages/ru/plugin.py` -> `core.verb_service.generate_and_promote_verb()`) has its own independent guard: an in-process dedup set plus the persisted `verb_pair_generation_attempts` marker described above, rather than the IP rate limiter (it's triggered by board rendering, not a search query) -- and is deliberately not duplicated by the general search-miss path, which generates only the queried aspect and lets pair completion fill the partner lazily on first view.

**Audio:**
- URL: `/audio/{language}/{verb_id}/{voice}/{form_key}.mp3`
- `form_key` = `build_hashed_audio_key(base_key, text)` = `{base_key}_{sha1(text)[:10]}` -- content-addressed
- On-demand: endpoint loads verb, walks board rows/examples to find matching hash, calls `ensure_audio()`
- Pre-warm: `_warm_verb_audio()` in `admin_candidates.py` generates both voices on verb add/regenerate
- `_NO_AUDIO_ROW_KEYS = {"aspect", "pair", "binyan", "root"}` -- no audio button for these rows

**Auth and progress sync:**
- Firebase Auth via `auth.js` (deferred); `authReadyPromise` resolves once per page load
- On login: `hydrateProgress()` union-merges server state into localStorage (never deletes local knowledge); dispatches `vb:progress-hydrated`
- First sign-in upload: local-only known verbs not yet on server are batch-uploaded via `POST /api/progress/known/batch` (`{language, verb_ids}`, up to 2000 per request) during `hydrateProgress()` -- `auth.js`'s `uploadKnownBatch()` chunks client-side at 500 and retries each chunk once on failure (`console.warn`s if still failing), instead of the old one-`fetch`-per-verb approach with no concurrency cap and a silently-swallowed `.catch()`. Server-side, `set_known_batch()` (`core/progress/progress_repository.py`) commits in Firestore-batch-sized groups of 400 and does one batched `db.get_all()` read per chunk (not one `.get()` per verb) to decide which verbs still need their SRS ladder seeded.
- On sign-out: dispatches `vb:auth-signed-out` -- only when transitioning from logged-in to null
- Badge merge: keep whichever list (local vs server) is longer; local-only badges are uploaded to server on `vb:progress-hydrated`; `syncPracticeBadgesFromServer()` called inside that handler

**Practice loop:**
- Session: `localStorage` key `practice_session:{lang}` -- `{ids, lemmas, size}`; sizes 3/6/9
- Audio listens per verb: 3 / 5 / All (configurable; stored in `practice_min_plays` localStorage key)
- Requires N audio plays before Next; on the last verb Next calls `_finishPractice()` (no separate Finish button)
- Skip = "Skip & mark as learned" -- marks verb as known and removes it from the session
- **Sign-in gate on Start (owner decision 2026-09-25):** an anonymous visitor must sign in (free Google sign-in) to START a practice session, for every study language including English and Russian; verb pages, audio, search, marking verbs known and the Verb of the Day stay open. `practice_loop.js`'s Start click goes through `requestStartPractice()`: if Firebase auth is available (config apiKey, SDK loaded, `VerbBoardAuth`) it waits up to 1.5 s for auth and, when there is no user, shows a modal (`showSignInGate()`, reusing the wrap-up overlay/card CSS plus `.practice-gate-*` in `verbs.css`; strings `practice.gate_title/body/cta/note/dismiss` in all 4 locales and whitelisted in `app/routes/verbs.py`'s `ui_strings`) instead of starting; its CTA calls the existing `VerbBoardAuth.signIn()` (Android one-tap redirect, iOS two-tap page), so on desktop (popup sign-in) the open gate closes on `vb:progress-hydrated` and practice starts automatically, while redirect/two-tap sign-in reloads the page and the user taps Start again. It **fails open**: no config, SDK blocked/failed, auth not resolved in time, or an embedded in-app browser (Instagram/Facebook/LinkedIn/Android WebView user agents, where Google blocks OAuth so a gate would be a dead end) starts practice as before, which is also why the e2e harness (Firebase SDK blocked) is unaffected. It is a soft product gate, not a security boundary (completing a practice already needs auth server-side via `/api/progress/practice`); an in-progress `practice_session:{lang}` and its Continue link are untouched so nobody is dropped mid-session. Consequence for metrics: anonymous `practice_started` now stops appearing (except from embedded in-app browsers, which fail open and never show up in `practice_gate_shown`); the new session flag `practice_gate_shown` (POST `/api/analytics/practice_event {event:'gate_shown'}`, set-once, no stub doc) plus the session's `uid` gives the gate's conversion, shown in the admin usage summary as "Practice gate shown" / "...then signed in". Tested in `tests/e2e/test_practice_gate.py` (stubbed Firebase). Known pre-existing quirk: the wrap-up modal, also attached to `<body>`, renders in the browser default serif font (the gate card sets its own font).
- **Repeat quota for seen-but-not-known verbs (issue #19):** `startPractice()` builds a session in three slices -- up to `max(1, floor(size/3))` SRS-due review verbs (known verbs only, unchanged), up to the same number of *repeat* verbs, and the remainder new verbs. Repeat verbs are those in `seen:{lang}` and not in `known:{lang}` (a verb becomes seen when its page is viewed, so anything practiced but never starred returns), picked by `pickRepeatCandidates()` -- a pure function exported on `window.VerbBoardPracticeLoop` and unit-tested from Node in `tests/test_practice_repeat.py` -- longest-waiting first, with never-repeated verbs first and ties random. It records `Date.now()` per repeat-picked verb in localStorage `practice_last_repeated:{lang}` (verbId -> ms; local only, like the session), which is what turns "better odds" into a guarantee that every stuck verb resurfaces in turn. Repeat picks use the ordinary `'new'` mode (normal Next/Skip bar), so `learn_practice.js` is unchanged. Deliberately separate from SRS: SRS ladders only start once a verb is marked known; this covers the pre-known phase.
- Completion earns a badge (session size appended to `badges` list)
- `BADGE_COMPACT_THRESHOLD` (from `VB_BADGE_COMPACT_THRESHOLD`) switches to compact grouped badge display
- Wrap-up modal on return to verbs page (`practice_wrapup:{lang}`)
- Day streak feature removed entirely (2026-07-29, owner call -- "not my game"); see `PRODUCT_BACKLOG.md` for the removal record if the mechanism needs to be understood historically

**Login nudge (anonymous-only):** built to close a measured gap (95.7% of engaged sessions in a 60-day analytics window never log in, and there was previously zero in-context sign-in prompt on `/learn` or `/verbs`, only the unlabeled person-icon in the bottom nav). One localStorage counter (`login_nudge_score`) accumulates three weighted signals -- verb page view +1 (`learn.js`), marking a verb known +3 (`learn.js`'s `toggleKnown()`), finishing a practice session/earning a badge +10 (`learn_practice.js`'s `_finishPractice()`) -- all logic lives in `app/static/login_nudge.js`, imported on both `board.html` and `verbs.html`. Two delivery surfaces share this one mechanism: badge-earned always fires immediately as a CTA row added to the existing practice wrap-up modal (`practice_loop.js`'s `showWrapUp()`), bypassing the dismissal cooldown entirely -- the only thing that can suppress it is a lifetime cap of 5 total shows (`login_nudge_shows_count`); separately, a score >= 12 without badge having fired yet shows a dismissible inline card at the top of `/verbs` (`login_nudge_card.js`, rendered into `#vb-login-nudge-slot` in `verbs.html`), catching an engaged browse-and-star user who never starts a practice session. Dismissing the card sets `login_nudge_dismissed_at_score`; it won't reshow until the running score roughly doubles from that value. `reserveThisPageLoad()` synchronously claims the "only one surface per page load" slot before either surface's async auth check resolves -- added after code review flagged that the guarantee was otherwise correct only by coincidence of script order and promise timing, not by design. `whenAuthReady()` waits for Firebase auth to resolve and live-rechecks `window.VerbBoardAuth.currentUser()` before rendering, specifically to avoid replaying the CTA to a user who signed in after a stale `practice_wrapup:{lang}` payload was written (tab killed before the redirect to `/verbs` completed). The CTA button calls the existing `window.VerbBoardAuth.signIn()` -- no new sign-in UI. No new endpoints, no new cookies, no server-side state at all; new i18n keys `login_nudge.badge` and `login_nudge.progress` in all 4 locale files (`app/i18n/{en,ru,he,es}.json`). Tested in `tests/test_login_nudge.py` (14 tests) via the same Node-subprocess harness pattern as `tests/test_srs_merge.py` -- loads the real JS file and drives its exported functions directly from pytest.

**Spaced repetition (Anki-style, free tier):** a verb enters a Leitner box ladder (`LEITNER_INTERVAL_DAYS = (1, 3, 7, 16, 35)` in `core/progress/models.py`) the first time it's marked `known` (star toggle or "Skip & mark as learned") -- `known` doubles as "entered the review ladder," there is no separate opt-in. Pure box-transition rule is `leitner_next_box()` (Python) / `nextBox()` in `app/static/srs.js` (JS) -- keep both in lockstep, see `tests/test_srs_merge.py` for the Node-subprocess parity harness (same pattern the removed `streak.js`/`streak.py` used). No SM-2/ease-factor math: the only signal is a binary self-report ("Knew it" / "Show me again") on resurfaced verbs during a normal practice session -- there is no separate review screen. `srs_box`/`srs_due_at`/`srs_reviewed_at` live on the existing `user_progress/{uid}/languages/{lang}/verbs/{verb_id}` doc (no new collections); `POST /api/progress/review` advances the box server-side (single source of truth); `GET /api/progress` includes the fields when `srs_box > 0`. Due-ness is computed client-side (`srs.js`'s `getDueVerbIds`) from data `hydrateProgress()` already fetches -- no server-side due query, no Cloud Scheduler, no background job. `practice_loop.js`'s `startPractice()` mixes due-and-known verbs into the session (capped at ~1/3 of session size) via `dueReviewCandidates()`, tagging each verb's mode (`'review'` vs `'new'`) in the session's `modes` map (absent key = `'new'`, for backward compat with in-flight sessions from before this shipped); `learn_practice.js`'s practice bar shows the recall buttons only for `mode === 'review'` verbs. **Sync model deliberately differs from seen/known**: SRS state mutates in both directions (box/due-date can move either way across devices), so `srs.js`'s `mergeFromServer()` (called from `hydrateProgress()`) is last-write-wins by `srs_reviewed_at`, not the union-merge-never-delete rule the rest of progress sync uses -- do not fold SRS fields into the existing union-merge loop.

**Verb of the Day:** One featured verb per language per day, shown as a chip on the home page (`/`). `get_verb_of_the_day(entries, *, language, date_str)` in `core/verb_loader.py` is the entry point (`app/routes/home.py`'s `home()` GET handler calls this, not `pick_verb_of_the_day()` directly). `pick_verb_of_the_day()` is the deterministic hash algorithm alone -- hashes `f"{language}|{date_str}"` with SHA-256, indexes into `entries` sorted by verb id (not the caller's rank order) modulo the entry count -- but that algorithm's stability guarantee breaks the moment the demand-driven generation pipeline adds a verb mid-day, since that changes `len(entries)` and therefore the index (found+fixed 2026-09-16, issue #40: the original design assumed catalog size only changed via infrequent admin action, which stopped being true once autogen started running on every unauthenticated search-miss). `get_verb_of_the_day()` persists the day's first computed pick to a small `verb_of_the_day/{language}_{date}` Firestore doc (`{language, date, verb_id}`) via `doc_ref.create()` -- same idempotent-first-write-wins idiom as `core.analytics.session_tracker._create_session()` (an `AlreadyExists` race loser re-reads and defers to the winner) -- so every subsequent read for that (language, date), from any Cloud Run instance, returns the same stored verb_id regardless of later catalog-size changes or per-instance `_ENTRIES_CACHE` differences. This is a deliberate small addition to Firestore reads/writes (one extra doc per language per day) over the original "no new storage" design, traded for an actual stability guarantee instead of one that silently stopped holding. Wired into `app/routes/home.py`'s `home()` GET handler, computed once per request and wrapped in try/except (logs and falls back to no chip on failure). Rendered in `app/templates/home.html` as `<a class="votd-hero">` (CSS in `app/static/home.css`), linking to `/learn?language=...&verb_id=...&ui_language=...`. As of 2026-09-16 (issue #33, home-funnel follow-up) it's the dominant above-the-fold element on the page -- moved out of the `.controls` card to render before the feedback/login row and language picker, since it's the only one-click path to real content and a funnel audit (#27) found ~70% of sessions never pick a language. New i18n key `home.verb_of_the_day` added to all 4 locale files (`app/i18n/{en,ru,he,es}.json`).

**Anki/CSV export of known verbs:** A button (`#vb-export-btn`) on the `/verbs` page (`app/templates/verbs.html`) exports the current language's known verbs as a two-column CSV (`lemma,translation`, no header row) that Anki's CSV importer reads directly -- aimed at power users who'd otherwise churn to Anki for spaced repetition. Pure client-side, no new backend endpoint: `app/static/verbs_export.js` reads the known-verb-id set already in localStorage (`window.VerbBoardStorage.readSet('known:' + language)`, the same per-language storage convention used elsewhere), and on click paginates the existing `/api/verbs` endpoint to fetch the full verb catalog for the language. The `translation` field on `/api/verbs` responses (and the shared `_build_verb_item()` in `app/routes/verbs.py` that also builds the initial page's embedded `window.VB_VERBS` blob) is opt-in via a new `&include_translations=1` query param, resolving `ui_lang` and reading `entry.lemma_translations.get(ui_lang, "")` only when requested -- this keeps the regular show-more/back-nav pagination payload (used by every `/verbs` page visitor, not just exporters) from growing for the ~100% of visitors who never export. The button's visibility check runs both on page load and on the `vb:progress-hydrated` event (dispatched by `auth.js`'s `hydrateProgress()`), not just once at `DOMContentLoaded`, because a logged-in user's known-verb list can arrive into localStorage asynchronously after page load via server-side hydration merge; checking only once at load would leave the button permanently hidden for exactly the returning, logged-in power users this feature targets. CSV values are defensively prefixed with a leading `'` when they start with `=`, `+`, `-`, or `@`, to neutralize spreadsheet formula injection if the file is ever opened in Excel/Numbers instead of imported into Anki.

**PWA / Mobile:**
- Manifest at `/static/manifest.json` (the `<link rel="manifest">` target; also served at `/manifest.json` by `well_known.py`), service worker at `/sw.js` (cache `vb-v54`), icons in `app/static/icons/`
- **Bump the SW cache version on every deploy that changes a precached static asset** (`PRECACHE` list in `sw.js`) -- the fetch handler is cache-first with no `clients.claim()`, so an unchanged cache name means returning visitors silently keep the old file forever (bit us once: a `learn.js` feature shipped but returning users saw no change and no error)
- Navigation requests (`e.request.mode === "navigate"`) are network-first with a fallback to the precached `/static/offline.html` on fetch failure -- pages are server-rendered/dynamic (Firestore-backed), so they are never cache-served; only static assets (CSS/JS/icons/svg) use the cache-first path
- Install prompt: `pwa.js` listens for `beforeinstallprompt` (must not be deferred); shows install button; on mobile tap shows hint, second tap triggers prompt
- 4-tab icon-only bottom nav (`_bottom_nav.html`): Back (chevron) / Verbs (list) / Search (magnifier) / Home (house); min-height 56px; uses `env(safe-area-inset-bottom)` padding; included on all pages; labels intentionally hardcoded English. The nav's own Login tab was removed (git commit `ed8b1be`, "bottom nav without login") -- sign-in entry points today are `auth.js`'s `mountAuthButton()` (renders into `#auth-slot`/`.page-header`/`.topbar-actions` where present) and the login-nudge CTA (card + practice wrap-up modal). `tapProfile()` in `auth.js` is orphaned dead code left over from the old Login tab; nothing calls it.
- Sign-in flow (`auth_pages.py` + `signin.html`): standalone PWA uses `window.open('/auth/signin', '_blank')`; mobile browser navigates to `/auth/signin?return_to=...`; desktop uses `signInWithPopup`. **One-tap mobile sign-in via `signInWithRedirect` (issue #55):** in `auth.js`'s mobile-browser (non-standalone) branch, `useRedirectSignIn()` decides between `signInWithRedirect` (one tap) and navigating to `/auth/signin` (two taps, the legacy flow). Per-device override in localStorage `vb_signin_redirect`: `?signin=redirect` sets `'1'` (force on), `?signin=popup` sets `'0'` (force off, the escape hatch), `?signin=default` removes it. With no override the platform default applies: ON for Android browsers (not WebViews, whose UA has `; wv)`), OFF elsewhere -- verified working on a real Android device (2026-09-25) but NOT yet on iOS Safari, so iPhone keeps the two-tap flow until someone tests it (`https://stage.verbboard.com/verbs?signin=redirect`). Standalone PWA and desktop are unchanged and ignore the flag, and `signin.html` stays as the standalone branch and the fallback. `initializeFirebase()` calls `getRedirectResult()` once per page load (no-op when nothing is pending; errors only `console.warn`) and deliberately does not consume the result, since `onAuthStateChanged` already does the post-sign-in work exactly once. **Cross-language search:**
- Endpoint: `GET /search_verb_by_lang?language={lang}&q={query}&source_lang=en`
- Calls `translate_search_query(query, source_lang, target_lang, project)` in `core/translation_service.py` via Vertex AI Gemini (`gemini-2.5-flash-lite`)
- Token fallback: Gemini may return "correr." with punctuation; each token is tried against `find_verb_by_search_extract`
- Fuzzy fallback: if Firestore misses, `load_entries_for_language` + `find_best_entry` scans cached verbs
- On success: redirects to `/learn` with `translated_from={original}&source_lang=en`; UI shows "Найдено через Английский: {original}"
- On translation failure: redirects with `not_available=1&search={original}&search_mode=en`
- On translation success but verb absent: logs demand signal with translated word; `search_mode=native`
- **GCP requirement:** Cloud Run service account needs `roles/aiplatform.user` to call Vertex AI

**Inline translations:** `Example.translations` dict; Claude/Gemini routing per language; shown when UI language differs from verb language. Verb infinitives are translated the same way via `lemma_translations` dict on `VerbEntry`/Firestore docs and `translate_lemma()` (mirrors `translate_examples()`); both share one toggle button, which sets `translations-visible` on `#learn-page` (not `.examples-table` -- broadened so the lemma-translation span outside the examples table is also gated). `tools/backfill_translations.py --field {examples,lemma,both}` backfills existing verbs (merged 2026-09-15 from two near-duplicate scripts, plus the redundant fr/it-specific one-off scripts; `--field` defaults to `both`). Claude's JSON output for lemma translation is unreliable for ambiguous/tricky lemmas (rambling commentary, self-correction loops) -- `_call_claude_lemma` extracts the last `{...}` block defensively rather than parsing the raw response, and the prompt has an explicit rule to silently pick one sense/conjugation-pattern without hedging. `translate_lemma()`/`translate_examples()` are two independent, non-fatal LLM calls during candidate generate/regenerate (`app/routes/admin_candidates.py`) -- a transient failure in just one can leave a candidate with (e.g.) a translated lemma but untranslated examples; `promote_candidate` re-runs both (no-op if already complete, since both functions only fill missing target languages) as a safety net immediately before writing the verb live. On-the-spot autogen (`core/verb_autogen.py`'s `_translate_new_verb()`) does the same for its generated verbs: examples AND lemma, into every UI language except the verb's own (Hebrew via Claude), non-fatal at each step. The targets come from `translation_service`'s defaults (derived from `UI_LANGUAGES`), not a per-language table: a hand-kept table there had left Hebrew out and never translated the lemma, so generated Italian/French verbs stayed untranslated for Hebrew-UI users until someone ran the backfill tool. Consequence worth knowing: whichever languages are in `UI_LANGUAGES` are the translation targets everywhere, so removing a UI language (e.g. Hebrew) there also stops translating into it. `tools/backfill_translations.py --language all` covers every study language (`ALL_STUDY_LANGUAGES`) as a source.

**Pronoun reference row (issue #32):** a collapsible "Pronouns" block (`<details class='pronoun-block'>`, native disclosure, collapsed by default) on the `/learn` board, positioned right after the metadata section and before the Examples heading. Shows all 6 grammatical persons (`PRONOUN_PERSONS = ("1sg", "2sg", "3sg", "1pl", "2pl", "3pl")`) for the study language, e.g. Italian renders io/tu/lui-lei/noi/voi/loro. Data is a small static table, `core/pronouns.py`'s `PRONOUNS` dict keyed by language, covering all 6 study languages (en/ru/he/es/it/fr) -- deliberately not routed through Firestore or `translate_lemma()`/`translate_examples()`, since it's a fixed 6-word-per-language closed vocabulary that never changes, and every study language also happens to be a valid UI-language lookup key in the same table (en/ru/he/es serve both roles), so a pronoun's "translation" is just the same-person row lookup in `PRONOUNS[ui_lang]` -- no per-language-pair translation data needed. Translation reveal is deliberately independent of the examples' inline-translation toggle (`#toggle-translations` / `translations-visible` on `#learn-page`) as of 2026-09-16 -- an earlier version reused that toggle, which repeatedly got mistaken for a rendering bug ("translation not visible") since a student had to notice and click a button unrelated to the block they'd just opened. Instead, `.pronoun-translation` reveals via a pure-CSS `.pronoun-block[open] .pronoun-translation:not(:empty)` rule keyed off `<details>`'s native `open` attribute: unwrapping Pronouns shows the translation immediately, no extra click, no JS. `has_any_translation` in `core/render.py` (which gates whether the *examples* toggle button renders) no longer factors in pronoun data at all -- that clause existed only to work around the old shared-toggle design and is gone now that pronouns don't need the button. Hebrew study-language pronoun words render RTL via the existing `label_dir` convention (same attribute used elsewhere in `render_board_html`); the UI-language gloss column uses `translation_dir` independently, so an RTL study language paired with an LTR UI language (or vice versa) renders each column in its own correct direction. Intentionally bypasses the sections/conjugation-table machinery (`NO_AUDIO_ROW_KEYS`, per-row audio buttons, gender/number focus filter, jump-to-example targeting) since none of that applies to a static, non-conjugated reference table. `.pronoun-table` must not set `border-collapse: collapse` -- the shared `table` rule in `learn.css` gives every table a card look via `border-radius` + `overflow: hidden`, and collapsed borders render incorrectly against that combination in most browsers (clips/hides the first and last rows) -- bit us once (2026-09-15), fixed by falling through to the default `border-collapse: separate`.

**Jump to example (from a conjugation form) -- currently switched OFF in every deployment (`JUMP_TO_EXAMPLE_ENABLED=false` in the Makefile and `cloudbuild.stage.yaml`; the setting defaults to on), so users do not see the 🔎 button and user-facing copy (About page, README) must not advertise it:** each conjugated form row gets a `data-form` attribute and a 🔎 button (`core/render.py`, only for rows with real audio and only when the verb has examples). **Analytics:** `_PageViewMiddleware` in `app/main.py` tracks page views on `/`, `/verbs`, `/learn`, `/feedback`. Session ID = `SHA256(forwarded_ip|user_agent|date)[:32]` -- no cookie needed. One `analytics_sessions` doc per (IP, UA, day) in Firestore (created with `create()`, idempotent). `analytics_daily` was dropped 2026-06-14 -- nothing writes to it anymore; `get_device_mix()` in `core/admin_feedback_service.py` derives all usage stats from `analytics_sessions` directly. UID attached to session on Firebase login via `POST /api/analytics/session` (server re-derives fingerprint from request headers). As of 2026-09-16 (issue #33), two diagnostic-only fields, both set-once like `device_type` (never overwritten by later enrich/update calls): `referrer` (from the `Referer` request header, truncated to 500 chars, captured only at session-creation time -- for segmenting #27's traffic-source hypotheses) and `sign_in_tapped_branch` (`standalone`/`mobile`/`desktop`, set via `POST /api/analytics/sign_in_tapped` from `auth.js`'s `signIn()` -- for #28's sign-in-friction hypothesis). A third pair, `practice_started`/`practice_completed` (both booleans, same set-once treatment, issue #48), closes a blind spot in the practice-conversion metric: `core/admin_feedback_service.py`'s existing practice count only scans the uid-keyed `user_practice` collection, but the practice loop itself (`practice_loop.js`) has no auth gate, so anonymous practice sessions were previously invisible to any metric. `practice_started` fires from `practice_loop.js`'s `startPractice()`; `practice_completed` fires from `learn_practice.js`'s `_finishPractice()`'s `if (accomplished)` branch only, and is deliberately independent of `practice_started` (a lost start beacon must not suppress the completion signal). As of 2026-09-24, two more set-once-per-day session fields: `home_viewed` (set by `_PageViewMiddleware` on a GET of `/`, flips false -> true like `verb_viewed`) and `votd_clicked` (set via `POST /api/analytics/votd_clicked` from `home.js`'s click listener on `.votd-hero`), together giving a Verb of the Day click-through rate (`votd_clicked` / `home_viewed`; sessions created before 2026-09-24 have no `home_viewed`, so restrict to later dates, and a click with no existing session doc is dropped rather than creating a stub). All three client beacons (`votd_clicked`, and both `practice_event` calls) use `fetch(..., {keepalive: true})` because each fires immediately before a navigation, when a plain in-flight fetch can be cancelled by the unload. Separately, `core/analytics/search_hits.py`'s `record_search_hit()` keeps one `verb_search_hits/{language}_{verb_id}` doc per verb with an atomically incremented `hits` counter (plus `hits_search`/`hits_search_by_lang`, `last_hit_at`), called at the three search-hit redirect sites in `app/routes/home.py` -- `demand_signal` only records searches that *miss*, so before this there was no way to tell whether verbs generated by autogen were ever searched for again; join against `verb_candidates` docs with `source == "autogen"` (the live `verbs` doc carries no autogen marker) to isolate them. As of 2026-09-24 `detect_device_type()` (`core/analytics/client_context.py`) returns `"bot"` for self-identified crawlers/scanners/scripted clients (crude regex on the user agent; undeclared bots spoofing a browser UA are not caught -- a 3-day prod log sample found ~33% of tracked page views were self-identified bots, which had been inflating every session ratio), and `_read_sessions_summary()` counts those sessions as `bot_sessions` and leaves them out of every other figure. Sessions created before that date carry no bot label, so pre-2026-09-24 numbers are still mixed. `get_device_mix()` (`core/admin_feedback_service.py`) feeds these to the admin Feedback page's Usage summary card as an "Engagement" column (home viewed, Verb of the Day clicked + rate, practice started/completed, generated verbs and how many were searched again) and a "Top searched verbs" list, via `_read_sessions_summary()`'s `engagement` counts and `_read_search_hits_summary()`. `ui_lang_selected` (added 2026-09-25 for the Hebrew UI review, issue #60) is the UI language a visitor deliberately picked in the home page's globe dropdown, set via `POST /api/analytics/ui_lang_selected` from `home.js` (latest pick wins, validated against `UI_LANGUAGES`, dropped if the session doc doesn't exist); it separates deliberate selection from a UI language that came from the browser's Accept-Language or a saved preference (`resolve_ui_language()` falls back to the `Accept-Language` header), and the admin usage summary shows the counts (bots excluded). **Do not group visitors by `httpRequest.remoteIp` in Cloud Run request logs.** Behind Firebase Hosting that field is a Google proxy egress address (`74.125.x`, `192.178.x`, `66.102.x`) that changes on every request, not the end user's IP: five requests from one machine logged as five different IPs (verified 2026-09-25). Anything that treats it as a visitor id makes every hit look like a distinct visitor, e.g. a log-derived "bounce rate" came out at 87% single-hit and was an artifact (`analytics_sessions` had 48-66 sessions/day against 117-182 log "visitors"). The real client address is the first `X-Forwarded-For` hop, which the logs don't record; only the app's own session fingerprint (`get_fingerprint_sid`) sees it. Bounce vs repeat-visit (issue #47) therefore has to be measured in the app, not derived from logs. Older `sign_in_tapped_branch` and `referrer` still have no consumer beyond raw Firestore inspection.

## Conventions & Constraints

- No frontend frameworks -- vanilla JS only
- No second database -- Firestore is the single source of truth
- Do not commit `.env` or secrets
- **Never use `set_cookie()` for non-`__session` names** -- Firebase Hosting CDN strips all other cookies before forwarding to Cloud Run and before returning responses to the browser
- When adding a feature: does it conflict with the stateless/frictionless UX principle?
- Always read `Makefile` and `pytest.ini` before touching test config

## Testing

```bash
pytest       # run all tests
make test    # check Makefile first
```

- `pytest.ini` is present -- read before adding pytest config
- Tests live in `tests/`
- Use the **qa-engineer** agent for writing and maintaining tests
- Playwright e2e tests leave a running asyncio loop -- run async test coroutines in a `ThreadPoolExecutor` worker thread (see `tests/test_audio.py` for the pattern)
- **Firestore in tests (issue #8):** `tests/fake_firestore.py` (`FakeFirestore`/`FakeCollection`/`FakeDocRef`/`FakeSnapshot`/`FakeBatch`) is an in-memory fake covering the subset of the Firestore client API this codebase's write paths use -- `.create()` raises `AlreadyExists`, `.update()` raises `NotFound` on a missing doc, `.set(merge=True)` shallow-merges, `collection_group()` reports a real `.reference.path` (docs are stored flat, keyed by full slash-joined path, so path-parsing callers like `admin_feedback_service._read_practice_summary` work against it); `firestore.Increment` is resolved (added to the existing numeric field) on set/create/update, so counter tests can assert real totals; other sentinels are stored opaquely. **No unit test can reach the real project:** the autouse `_no_real_firestore` fixture in `tests/conftest.py` pre-seeds `core.storage.firestore_db._db` (the lazily-built client singleton behind `get_db()`) with a fresh per-test `FakeFirestore`, which covers every import style of `get_db` and keeps the "empty / not found" behavior tests used to get implicitly. It also resets `verb_loader._ENTRIES_CACHE` per test. This exists because `.env` points `GOOGLE_CLOUD_PROJECT` at the live project and dev machines have valid ADC, so a test that forgot to mock Firestore used to read and write live data (search tests once incremented real `verb_search_hits` counters), hidden by every writer's `except Exception`. `tests/e2e` is exempt on purpose (its in-process server reads the live project); tests that patch `get_db` themselves still win. Request the `fake_db` fixture to seed or inspect state (it returns the same per-test instance); `seed_spanish_verb(fake_db)` in `tests/conftest.py` puts one minimal verb in. Non-Firestore live services (Vertex/Gemini, Anthropic) are not guarded. Six older ad-hoc `_FakeDb`-style mocks remain scattered across the suite; they are not migrated. **Patching a name that other modules also import (issue #58):** a plain `monkeypatch.setattr("core.x.name", ...)` on the *defining* module silently stops applying the moment a consumer does a module-scope `from core.x import name`, and `assert_not_called()` then false-greens. Use `patch_everywhere(monkeypatch, "core.x.name", replacement)` from `tests/conftest.py` (identity-matches every loaded `app.*`/`core.*` module holding the same object and patches them all), or patch the *consuming* module's own name. `tests/test_patch_targets.py` fails with file:line and the holder modules if a test patches a defining-module name that others hold; the `get_db` sites are allowlisted there (the autouse guard already covers them; moving them off string patches is #58 step 3). Examples of state-assertion tests on the shared fake: `tests/test_admin_feedback_service.py`, `tests/test_session_tracker.py`.
