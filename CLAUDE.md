# CLAUDE.md — VerbBoard Project Context

@AGENTS.md
@workflow.md

VerbBoard is a verb-focused language learning app: conjugation tables, real usage examples, audio, and practice loops. Unknown searches become demand signals that drive future verb coverage. FastAPI + server-rendered UI, GCP backend.

---

## Tech Stack

- **Backend:** Python 3.12 + FastAPI
- **Frontend:** Vanilla JS + CSS (no framework -- do not introduce one)
- **Data:** GCP Firestore (single source of truth in all environments)
- **Audio:** GCS-only (`AUDIO_BUCKET`); pluggable backend abstraction in `core/audio_backend/`
- **AI generation:** Anthropic Claude -- Haiku (`claude-haiku-4-5-20251001`) for English, Sonnet (`claude-sonnet-4-6`) for all others; GCP Gemini for translation workflows
- **Auth:** Firebase Auth (Google sign-in); server validates ID tokens on `/api/progress/*`
- **Secrets:** GCP Secret Manager (prod/stage) or `.env` (local)
- **Infrastructure:** GCP -- Cloud Run + Firestore + GCS
- **Cross-language search:** Vertex AI Gemini (`gemini-2.5-flash-lite`) translates EN query to target language lemma; `translate_search_query()` in `core/translation_service.py`
- **App entry point:** `app.main:app`

## Key Architectural Patterns

**Language plugins:** `core/languages/{lang}/plugin.py` self-registers on import (triggered in `app/main.py`). Each implements `build_board(verb, voice_key, voice_label) -> Board`.

**Firestore data model:**
- Verb collections: `verbs`, `verb_candidates`, `demand_signal`, `demand_signal_labels`
- Bookkeeping-only: `verb_pair_generation_attempts` -- one doc per (language, input lemma) that Claude either failed to generate or resolved to a different lemma than the lookup key, keyed by the *input* lemma's `verb_id` with an optional `resolved_verb_id` pointer; read by `core.verb_service.generate_and_promote_verb()` (Russian aspectual-pair generation, `core/languages/ru/plugin.py`) to skip a repeat Claude call within `_PAIR_ATTEMPT_RETRY_AFTER` (24h) instead of paying for one on every `/learn` render of a verb whose pair keeps missing. Never read as verb data.
- Bookkeeping-only: `verb_of_the_day` -- one doc per (language, date) (`{language, date, verb_id}`), doc id `{language}_{date}`, written once via `create()` on the first request of the day and read on every request thereafter by `core.verb_loader.get_verb_of_the_day()`. See the Verb of the Day pattern entry below for why this exists.
- Audio problem reports (issue #71): `audio_report_votes/{uid}_{sha1(language|verb_id|voice|form_key)[:16]}` (per-user dedupe marker, the only place a uid is stored, written with `create()`) and `audio_reports/{language}_{verb_id}_{voice}_{form_key}` (aggregate: `text`, `row_kind` form|example, `count`, `reasons.<reason>`, `ui_langs.<lang>`, `first_at`/`last_at`, up to 5 `comments`, `status` open|resolved). Never read as verb data.
- Doc ID: `{language}_{transliterated_lemma}` (e.g. `en_go`, `ru_idti`) -- Cyrillic/Hebrew transliterated to ASCII
- Key fields: `language`, `verb_id`, `lemma`, `rank`, `forms`, `examples`, `search_extract` (array), `morph`, `display_lemma`, `display_forms`
- Search: `find_verb_by_search_extract()` uses `array_contains` on normalized query
- User progress: `user_progress/{uid}/languages/{lang}/verbs/{verb_id}` -- `seen`, `known`, timestamps
- User practice: `user_practice/{uid}/languages/{lang}` -- `badges` (list of ints), `started_at`, `updated_at`
- Legacy fallback: old data at `user_progress/{uid}/verbs/{verb_id}` is read if new path is empty
- Security rules and composite indexes are tracked in source control (`firestore.rules`, `firestore.indexes.json`, both referenced from `firebase.json`'s `firestore` block) as of 2026-09-16 (issue #39) -- previously these existed only as manual console state with no way to recover them from git. `firestore.rules` is a verified byte-for-byte copy of the live deny-all ruleset (`allow read, write: if false` for all documents -- the app works only because the server exclusively uses the Admin SDK, which bypasses rules); `firestore.indexes.json` holds the 3 composite indexes that actually exist in the live project (pulled via `gcloud firestore indexes composite list`, not hand-derived from reading query code -- Firestore's automatic single-field indexing covers equality-only and equality+array-contains query combinations without an explicit composite index, so most `.where().where()` chains in this codebase, including the primary search path's `language ==` + `search_extract array-contains`, don't actually need one; a composite index is only required here for an equality filter combined with `order_by` on a different field, which is the one index that exists, for `list_verbs_recent()`). **Neither file is wired into the deploy pipeline yet** -- committing them is source-of-truth recovery only; `firebase deploy --only firestore` is deliberately not yet added to `cloudbuild.stage.yaml`/`Makefile` since that changes what happens on every future push (see the tracked follow-up issue). Drift detection exists instead as the read-only `tools/check_firestore_drift.py` (`make firestore-drift`): it compares the live ruleset and composite indexes against the committed files and exits 1 on any difference (checked clean on 2026-09-25); auto-deploying them remains an owner-sign-off decision tracked in #51.

**Demand-driven generation pipeline:** Unknown searches are logged as demand signals. Admin flow: review signals -> generate structured verb data via Claude + Gemini -> preview candidate on live `/learn` page -> promote to `verbs`. Admin triggers `_call_claude(language, query)` in `admin_candidates.py` (async) -> strict JSON -> stored as candidate. All AI config lives in `core/settings_ai.py`. Per-language system prompt via `get_cached_system(language)` with `cache_control: ephemeral`. Hebrew gets `max_tokens=4096`, others 2048. `promote_candidate`/`regenerate_verb`/`regen_verb_examples`/`regen_verb_forms` in `admin_candidates.py` all call `invalidate_entries_cache(language)` after writing the live `verbs` doc, so a promote/regen doesn't leave `/verbs`/`/learn` serving a stale cached list for up to `load_entries_for_language`'s 300s TTL.

**On-the-spot autogen abuse guard (EN/ES/IT/FR/RU search-miss path, and RU pair completion):** both `/search_verb_by_lang` and `/search_verb` (`app/routes/home.py`) are public, unauthenticated GET routes that can trigger a paid generation + auto-publish to live `verbs` when a search misses (`core.verb_autogen.autogenerate_missing_verb`). Generation is provider-dispatched per language (`core.verb_autogen._generate_verb_payload`): Gemini for EN/ES/IT/FR, Claude/Sonnet for Russian (`_CLAUDE_AUTOGEN_LANGUAGES`) -- matching this project's Sonnet-for-non-English convention rather than adding RU to the Gemini path. Russian's cold generation (no anchor verb, unlike pair completion below) goes through an extra `core.languages.ru.validation.validate_ru_payload()` gate before any live write -- checks aspect/tense-slot consistency and pair-field sanity; a failure writes a `verb_candidates` doc with `status="needs_review"` instead of publishing. `autogen_rate_limited(client_ip)` (`core/verb_autogen.py`, backed by `core/rate_limit.py`'s `SlidingWindowRateLimiter`) caps this at 5 triggers/10min per client IP, in-process/per-Cloud-Run-instance -- a soft, best-effort cap, not a hard security boundary, since Cloud Run can run multiple instances, shared across all languages/providers regardless of per-call cost. `_client_ip()` in `home.py` deliberately reads the *last* `X-Forwarded-For` hop (the one appended by infra closest to Cloud Run), not the first (client-supplied and spoofable) -- opposite of `core.analytics.session_tracker`'s fingerprint, which uses the first hop for best-effort analytics where spoofability doesn't matter. `build_storage_verb_id`'s Cyrillic transliteration can collide distinct lemmas (e.g. "сесть"/"съесть" both -> "ru_sest"); `_allocate_verb_id()`/`_allocate_candidate_doc_id()` fall through to a numbered suffix on a lemma/query mismatch rather than silently treating the collision as "already generated." Russian's separate, already-live pair-completion path (`core/languages/ru/plugin.py` -> `core.verb_service.generate_and_promote_verb()`) has its own independent guard: an in-process dedup set plus the persisted `verb_pair_generation_attempts` marker described above, rather than the IP rate limiter (it's triggered by board rendering, not a search query) -- and is deliberately not duplicated by the general search-miss path, which generates only the queried aspect and lets pair completion fill the partner lazily on first view.

**Anthropic outage handling (2026-10-05, account ran out of credit: HTTP 400 "credit balance is too low"):** `core/provider_health.py` holds an in-process `CircuitBreaker` (`ANTHROPIC`) wrapped, via `with ANTHROPIC.guard():` around only the API call (works around an `await` too), at every Claude call site: `verb_autogen._generate_verb_claude`, `verb_service.generate_and_promote_verb`, `translation_service._call_claude`/`_call_claude_lemma`, `admin_candidates._call_claude`/`_call_claude_single_example`, and `tools/bulk_generate.py` (aborts on a classified error). `classify(exc)` returns `out_of_credit` (400 whose whitespace-collapsed lowercase message contains "credit balance"/"billing"/"insufficient", or HTTP 402), `auth_error` (401/403: banner and 503 say "Claude API key rejected or lacks permission", not "top up"), `rate_limited` (RateLimitError) or `overloaded` (529); anything else is None and never trips it. While open, `guard()` raises `ProviderUnavailable(reason)` with zero network calls; cool-downs are the constants at the top of the module (out_of_credit and auth_error 120 s, rate_limited Retry-After or 60 s, overloaded 120 s), after which exactly one probe call goes through and success closes it; a probe that exits any other way (CancelledError, non-outage error) releases its slot, and a probe silent for 60 s (`PROBE_TIMEOUT_SECONDS`) is superseded. Per Cloud Run instance, so a second instance learns of an outage on its own first failing call. On open/close transitions only it writes `provider_status/anthropic` (`{state, reason, opened_at, updated_at, closed_at, last_error}`; `updated_at` is refreshed when a probe fails, and the admin banner ignores an `open` doc not refreshed for 30 min, so a scaled-down instance cannot leave it stuck) and logs `PROVIDER_UNAVAILABLE provider=anthropic reason=<reason>` (ERROR) / `PROVIDER_RECOVERED provider=anthropic` (INFO); set a Cloud Logging log-based alert on `textPayload:"PROVIDER_UNAVAILABLE provider=anthropic"`. Behavior while open: both search routes (for `_CLAUDE_AUTOGEN_LANGUAGES`, checked BEFORE `autogen_rate_limited` so no slot is spent) start no task and redirect with `not_available=1&search=..&queued=1` (never `generating=1`, so the 20 s reload loop does not start; `home.html` shows `home.search_queued`); the demand signal is still logged, with `provider_unavailable: true`; pair completion returns None and writes NO `generation_failed` marker; translations skip and leave the gap for `tools/backfill_translations.py`; only a failure of the primary admin generation (`_call_claude`, before any write) answers 503 `Claude unavailable (<reason>): <hint>`; a translation-step outage (incl. Hebrew-source) is skipped by `_translate_verb`/`_translate_examples_only` and generate/promote/regenerate/regen_examples/regen example return success with `translations_incomplete: true` (admin JS warns). Admin pages (home, feedback, reports, audio reports) show a red banner (`_provider_banner.html`) while the status doc is `open`. Deliberately no Gemini fallback for Russian/Hebrew (prompt/quality parity). Recovery: `make check-anthropic-credit`, then `make replay-failed-demand` (dry run, `--max-items` default 50, signals logged before `opened_at` need `--since`; `EXECUTE=1` generates; `tools/replay_failed_demand.py` also takes `--since/--until/--clear-pair-markers`, default window = last outage in the status doc), then `tools/backfill_translations.py --language all`. Simulate locally with `VB_FORCE_PROVIDER_DOWN=1` (ignored when the environment is prod; no status doc or logs are written for it). Tests: `tests/test_provider_health.py` (an autouse conftest fixture resets the global breaker).

**Audio:**
- **One bucket for every environment (2026-09-30):** stage, prod and local all use `verbboard-audio-prod` (Makefile `AUDIO_BUCKET_PROD`, `cloudbuild.stage.yaml`, `.env.sample`). The old per-environment split isolated nothing (same runtime service account on both buckets, same shared Firestore) and cost a second warm-up per language; audio keys are content-addressed (`{base_key}_{sha1(text)[:10]}`), so sharing is safe. `verbboard-audio-stage` is no longer used (kept ~30 days as a rollback, then delete); `cache-audio-stage`/`audit-audio-stage`/`clean-audio-stage` Make targets and `cache_audio.py --both-buckets` were removed. **Rule:** voice slots are keyed `female`/`male`, not by the TTS voice id, and clips are served `immutable`, so never trial a new voice against the shared bucket; swap voices only together with a full re-cache.
- URL: `/audio/{language}/{verb_id}/{voice}/{form_key}.mp3`
- `form_key` = `build_hashed_audio_key(base_key, text)` = `{base_key}_{sha1(text)[:10]}` -- content-addressed
- On-demand: endpoint loads verb, walks board rows/examples to find matching hash, calls `ensure_audio()`
- Pre-warm: `_warm_verb_audio()` in `admin_candidates.py` generates both voices on verb add/regenerate
- `_NO_AUDIO_ROW_KEYS = {"aspect", "pair", "binyan", "root"}` -- no audio button for these rows

**Auth and progress sync:**
- Firebase Auth via `auth.js` (deferred); `authReadyPromise` resolves once per page load
- On login: `hydrateProgress()` union-merges server state into localStorage (never deletes local knowledge); dispatches `vb:progress-hydrated`
- First sign-in upload: local-only known verbs not yet on server are batch-uploaded via `POST /api/progress/known/batch` (`{language, verb_ids}`, up to 2000 per request) during `hydrateProgress()` -- `auth.js`'s `uploadKnownBatch()` chunks client-side at 500 and retries each chunk once on failure (`console.warn`s if still failing), instead of the old one-`fetch`-per-verb approach with no concurrency cap and a silently-swallowed `.catch()`. Server-side, `set_known_batch()` (`core/progress/progress_repository.py`) commits in Firestore-batch-sized groups of 400 and does one batched `db.get_all()` read per chunk (not one `.get()` per verb) to decide which verbs still need their SRS ladder seeded.
- On sign-out: dispatches `vb:auth-signed-out` -- only when transitioning from logged-in to null
- Badge merge: keep whichever list (local vs server) is longer; local-only badges are uploaded to server on `vb:progress-hydrated`; `syncPracticeBadgesFromServer()` called inside that handler

**Audio problem reports (issue #71, 2026-10-04):** a signed-in learner flags one clip on `/learn`. `core/render.py` adds a `button.audio-report-btn` (outline flag SVG, filled when `aria-pressed`) after the play control of every form row and example row, plus one shared `#audio-report-pop` dialog in `board.html`; `app/static/audio_report.js` (one delegated listener) parses language/verb/voice/form_key from the sibling `<audio src>`, so no per-button data attributes. The button is shown to everyone: anonymous users get a toast (`audio_report.sign_in`) and `VerbBoardAuth.signIn()`; flags are dimmed (`#learn-page:not(.audio-played)`, class set on `vb:learn-audio-played`) until a clip has played. Reason tap sends immediately; "Add a note" reveals a 200-char `dir=auto` input, then reasons only select and Send submits. Filled/reported state follows the signed-in user across devices: it is cached in localStorage set `audio_reported:{lang}` of `verb:voice:form_key` (for instant paint) and, once per page load after auth resolves (and again on `vb:progress-hydrated`), `audio_report.js` calls `GET /api/audio_report/mine?language=&verb_id=` and union-merges the result into that set (never deleting local entries) then repaints. `mine_for_verb()` in the service runs ONE equality query on `audio_report_votes` (`uid`, `language`, `verb_id`; no composite index, reads only real votes, so no per-clip existence reads; vote docs written before the `uid` field was added are not returned, harmless since the feature was not live on prod yet). The `uid` field lives only on the vote doc, never in the aggregate or admin view. `core.audio_service.iter_board_clips()` is the shared board-to-clip-key enumeration behind `find_clip_text()`. It returns only `{reported:[{voice,form_key}]}` for the caller's own votes (401 anonymous, 400 bad language, separate 120/10 min per-uid limiter). Other users' reports stay invisible so counts remain independent. `POST /api/audio_report` (`app/routes/api_audio_report.py`, thin) requires the Firebase ID token (401 otherwise) and calls `core/audio_report_service.py`: validates language/voice/reason, per-uid `SlidingWindowRateLimiter` (20/10 min, 429), resolves `form_key` against the verb's board with `core.audio_service.find_clip_text()` (shared with `app/routes/audio.py`'s on-demand generator; the TTS text is never taken from the client; unknown key 404), writes the vote doc (`AlreadyExists` -> `{ok:true,duplicate:true}`, no increment) then merges the aggregate (a new report on a resolved clip reopens it). "Mark resolved" (admin, `resolve_audio_report()`) also deletes the user votes for that clip, so the same user can report it again if it is still wrong and their reported flag clears on the next page load (signed in, `audio_report.js` treats the `/mine` result as the source of truth for that verb, replacing the local entries for it), and it restarts the counters (`count`, `reasons`, `ui_langs`, `comments`) with the old total kept as `resolved_count`, so the admin ranking reflects only reports made after the fix. **Admin page `/admin/audio-reports`** (`app/routes/admin_audio_reports.py`, `admin_audio_reports.html`, `admin_audio_reports.js`; the card moved out of `/admin/reports`, linked from every admin nav): Open | Confirmed | Resolved tabs plus a language filter, `GET /admin/api/audio-reports?status=&language=` (status filtered by Firestore equality, sorted in Python, no composite index: open by count desc, confirmed by `confirmed_at` desc, resolved by `resolved_at` desc; confirmed rows show "+N since confirmed"); `admin_audio_reports.js` escapes every value and comment. **States** on the aggregate doc: `status` open | confirmed | resolved, plus `confirmed_at`, `confirmed_by` (always `"admin"`: the admin session has no per-person identity), `confirmed_voice_id`, `reports_since_confirm`, `resolved_at`, `resolved_count`. `POST /admin/api/audio-reports/{id}/{confirm|unconfirm|resolve}` (`transition_audio_report()`, ordered updates not a transaction; unknown id 404, wrong source state 409): open -confirm-> confirmed (records the Edge voice id of that doc's voice); open|confirmed -resolve-> resolved (fixed or dismissed, clears the public flag); confirmed -unconfirm-> open; there is no separate "fixed" action. resolve deletes the user votes and restart the counters (old total in `resolved_count`). `submit_audio_report` keeps a confirmed doc confirmed and only bumps count/reasons/comments plus `reports_since_confirm`; an open doc stays open; a resolved doc reopens. **Public "known audio issue" flag:** `confirmed_form_keys(language, verb_id)` (one equality query on language/verb_id/status=='confirmed', 60 s in-process cache per (language, verb_id), invalidated by every transition on that instance, returns an empty set and logs on any error so the board always renders) is read by `render_board_html()`; a form is flagged if EITHER voice's doc is confirmed (both voices read the same text), and for every flagged form row and example row the report flag is replaced by `.audio-issue` (an amber triangle `.audio-issue-btn` carrying the note in `data-note` (`audio_issue.note`, label `audio_issue.label`, both in all 4 locales); `audio_report.js` shows it in ONE shared body-level `#audio-issue-note` popover clamped to the viewport and flipped above when low, because an in-table panel was clipped by the tables' `overflow:hidden`; closes on Escape (focus returns), outside click, scroll, resize). Two auto-clear mechanisms: the flag only shows while `confirmed_voice_id` equals the CURRENT Edge voice id for that voice (a voice swap keeps the form_key since the text is unchanged, so this clears it), and a text change gives a new `form_key` so the old doc matches no clip. Other instances can show a stale flag for up to 60 s after a transition. Tested in `tests/test_audio_issue_flag.py`. `tests/fake_firestore.py` now deep-merges nested dicts and resolves nested `Increment` and `ArrayUnion` for `set(merge=True)`. Tested in `tests/test_audio_report.py`.

**Practice loop:**
- Session: `localStorage` key `practice_session:{lang}` -- `{ids, lemmas, size}`; sizes 3/6/9
- Audio listens per verb: 3 / 5 / All (configurable; stored in `practice_min_plays` localStorage key)
- Review-mode verbs show the ungated "Recalled it" button (the only SRS control) plus the same listen-gated ">" / "Finish" pill as new-mode, as an outlined secondary with no SRS effect (see Spaced repetition). Advancing clicks set an in-memory `advancing` lock (Next/recall disabled; Prev/Abandon stay live), cleared on a bfcache `pageshow`; `applyReview` is raced against a 3s timeout so a stalled request never blocks advancing
- Requires N audio plays before Next; on the last new-mode verb Next becomes a labeled "✓ Finish" pill (`practice-nav-btn--finish`, i18n `practice.finish`; `aria-disabled` and dimmed until the listen goal is met, flipped by `syncFinishState()` on mount and on `vb:learn-audio-played`; a tap before the goal still shows the listen warning) that calls `_finishPractice()`, which first bails to `/verbs` if `practice_session:{lang}` is gone (stale bfcache page must not award a second badge); no separate Finish button elsewhere
- **"Skip & mark as learned" removed entirely (owner decision 2026-09-28):** it used to sit next to Next in the non-review bar, calling `progress.setKnown(language, verbId, true)` and removing the verb from the session immediately -- bypassing the listen-gate that Next enforces, with no bypass mechanism replacing it. Removed rather than relabeled: the wording was confusing relative to the star's "known" language, and the bypass-listen-gate capability wasn't worth keeping a dedicated control for. Next is now the only advance control for new-mode verbs and always enforces the listen gate. Learners without a fast bypass just use Next normally, or use the star directly on the board page if they want to mark a verb known without going through the practice flow. `.practice-skip-btn` CSS (`common.css`) and the `practice.skip` i18n key (all 4 locales) were deleted along with it.
- **Sign-in gate on Start (owner decision 2026-09-25):** an anonymous visitor must sign in (free Google sign-in) to START a practice session, for every study language including English and Russian; verb pages, audio, search, marking verbs known and the Verb of the Day stay open. `practice_loop.js`'s Start click goes through `requestStartPractice()`: if Firebase auth is available (config apiKey, SDK loaded, `VerbBoardAuth`) it waits up to 1.5 s for auth and, when there is no user, shows a modal (`showSignInGate()`, reusing the wrap-up overlay/card CSS plus `.practice-gate-*` in `verbs.css`; strings `practice.gate_title/body/cta/note/dismiss` in all 4 locales and whitelisted in `app/routes/verbs.py`'s `ui_strings`) instead of starting; its CTA calls the existing `VerbBoardAuth.signIn()` (Android one-tap redirect, iOS two-tap page), so on desktop (popup sign-in) the open gate closes on `vb:progress-hydrated` and practice starts automatically, while redirect/two-tap sign-in reloads the page and the user taps Start again. It **fails open**: no config, SDK blocked/failed, auth not resolved in time, or an embedded in-app browser (Instagram/Facebook/LinkedIn/Android WebView user agents, where Google blocks OAuth so a gate would be a dead end) starts practice as before, which is also why the e2e harness (Firebase SDK blocked) is unaffected. It is a soft product gate, not a security boundary (completing a practice already needs auth server-side via `/api/progress/practice`); an in-progress `practice_session:{lang}` and its Continue link are untouched so nobody is dropped mid-session. Consequence for metrics: anonymous `practice_started` now stops appearing (except from embedded in-app browsers, which fail open and never show up in `practice_gate_shown`); the new session flag `practice_gate_shown` (POST `/api/analytics/practice_event {event:'gate_shown'}`, set-once, no stub doc) plus the session's `uid` gives the gate's conversion, shown in the admin usage summary as "Practice gate shown" / "...then signed in". Tested in `tests/e2e/test_practice_gate.py` (stubbed Firebase). Known pre-existing quirk: the wrap-up modal, also attached to `<body>`, renders in the browser default serif font (the gate card sets its own font).
- **Repeat quota for seen-but-not-known verbs (issue #19):** `startPractice()` builds a session in three slices -- up to `max(1, floor(size/3))` SRS-due review verbs (known verbs only, unchanged), up to the same number of *repeat* verbs, and the remainder new verbs. Repeat verbs are those in `seen:{lang}` and not in `known:{lang}` (a verb becomes seen when its page is viewed, so anything practiced but never starred returns), picked by `pickRepeatCandidates()` -- a pure function exported on `window.VerbBoardPracticeLoop` and unit-tested from Node in `tests/test_practice_repeat.py` -- longest-waiting first, with never-repeated verbs first and ties random. **Spaced repetition (Anki-style, free tier):** a verb enters a Leitner box ladder (`LEITNER_INTERVAL_DAYS = (1, 3, 7, 16, 35)` in `core/progress/models.py`) the first time it's marked `known` (star toggle) -- `known` doubles as "entered the review ladder," there is no separate opt-in. **Unmarking known exits the ladder (fixed 2026-09-28, owner-reported bug -- "leaher"/to delay kept showing the recall buttons after being unstarred):** `core/progress/progress_repository.py`'s `set_known(known=False)` now unconditionally resets `srs_box`/`srs_due_at`/`srs_reviewed_at` to `0`/`None`/`None` (the same "not in ladder" sentinel `list_progress_for_language()`/`GET /api/progress` already treat a missing/zero box as), and `app/static/srs.js`'s new `clearVerb(language, verbId)` deletes the verb's entry from the local `srs:{lang}` map, called from `progress.js`'s `setKnown()` on `known === false`. This reverses the ladder's original design (a verb the user marks known once and then unstars used to keep its box/due date, on the theory it was a rare edge case not worth extra write-path complexity) -- unstarring now means "stop quizzing me on this." Re-starring later is a fresh box=1 entry, not a resume, since the clear leaves no prior box to resume from; `set_known(known=True)`'s existing "only seed if no `srs_box` already present" guard is unchanged and, post-fix, mainly protects the rarer case of a client re-sending `known=True` while an in-flight or failed `known=False` clear hasn't landed yet (see `tests/test_progress_repository.py`'s `test_set_known_true_does_not_reset_existing_srs_box`). Pure box-transition rule is `leitner_next_box()` (Python) / `nextBox()` in `app/static/srs.js` (JS) -- keep both in lockstep, see `tests/test_srs_merge.py` for the Node-subprocess parity harness (same pattern the removed `streak.js`/`streak.py` used). No SM-2/ease-factor math: the only signal is a single "Recalled it" self-report (there is no down-signal; the neutral ">" below changes nothing in the ladder) on resurfaced verbs during a normal practice session -- there is no separate review screen. `srs_box`/`srs_due_at`/`srs_reviewed_at` live on the existing `user_progress/{uid}/languages/{lang}/verbs/{verb_id}` doc (no new collections); `POST /api/progress/review` advances the box server-side (single source of truth); `GET /api/progress` includes the fields when `srs_box > 0`. Due-ness is computed client-side (`srs.js`'s `getDueVerbIds`) from data `hydrateProgress()` already fetches -- no server-side due query, no Cloud Scheduler, no background job. `practice_loop.js`'s `startPractice()` mixes due-and-known verbs into the session (capped at ~1/3 of session size) via `dueReviewCandidates()`, tagging each verb's mode (`'review'` vs `'new'`) in the session's `modes` map (absent key = `'new'`, for backward compat with in-flight sessions from before this shipped); `learn_practice.js`'s practice bar shows the recall button only for `mode === 'review'` verbs. **"Recalled it" is the only SRS control; ">" is a neutral listen-then-continue path (owner decision 2026-09-30, partly reversing the 2026-09-28 "only control" rule):** a review-mode verb shows two advance controls. `recallYesBtn` (`_advanceAfterKnew()` in `learn_practice.js`, ungated) always calls `applyReview(language, verbId, true)` and is the visual primary (green pill); `nextBtn`, the same ">" (or labeled "Finish" pill on the last verb) as new-mode, is a secondary outlined circle, gated by `hasListened()` exactly like new-mode (tap before the goal shows the listen warning), and advances WITHOUT calling `applyReview` -- no box change, no credit, so a learner who does not remember the verb listens, reaches the listen count and moves on. It is not a down-signal: the removed "Show me again" button (`recallNoBtn`) was a labeled demote that behaved like "Recalled it" (label/behavior mismatch); ">" claims nothing, demotes nothing, and there is still no in-session "I forgot this" action -- unstarring resets `srs_box`/`srs_due_at`/`srs_reviewed_at` to the not-in-ladder sentinel, and the seen/known repeat-candidate logic resurfaces never-starred verbs. A review verb that is merely skipped with ">" is not rescheduled (its due date is unchanged, so it can reappear next session). On narrow screens the ">" stays on row 1 with Prev/counter and the recall pill keeps its own row 2 (mobile `order` block unchanged). `.practice-recall-group`'s wrapper `<div>` was also removed (`recallYesBtn` mounts directly in the practice bar, like `nextBtn` does for non-review mode); `.practice-recall-btn--no` and the `practice.recall_no` i18n key were deleted (all 4 locales). **Recall self-report is not gated behind the audio-listen requirement (fixed 2026-09-28, issue reported as "buttons do nothing"):** `nextBtn` (new-verb mode) still requires `hasListened()` (>= `PRACTICE_MIN_PLAYS` plays) before advancing -- that's the intended first-exposure drill -- but `recallYesBtn` does not, and never falls back to a warning toast (the review-mode `nextBtn` is gated like new-mode, but it is not the recall control). Review verbs are, by construction, already-starred/known verbs being recall-tested; forcing several audio replays before the learner is allowed to self-report "Recalled it" force-feeds the answer immediately before the test and, with no Skip fallback in review mode, previously left a learner short of the listen count with no way to advance at all except an easy-to-miss 2.5s amber toast -- read by the reporting learner as "the buttons do nothing." Audio remains available as an optional aid; it's just no longer a prerequisite. `_finishPractice()`'s badge-completion check (`accomplished`) was updated in lockstep: it now skips the listen-count requirement specifically for ids whose `session.modes[id] === 'review'`, so a session containing review verbs doesn't lose its badge purely because those verbs weren't replayed enough. **Sync model deliberately differs from seen/known**: SRS state mutates in both directions (box/due-date can move either way across devices), so `srs.js`'s `mergeFromServer()` (called from `hydrateProgress()`) is last-write-wins by `srs_reviewed_at`, not the union-merge-never-delete rule the rest of progress sync uses -- do not fold SRS fields into the existing union-merge loop.

**Verb of the Day:** One featured verb per language per day, shown as a chip on the home page (`/`). `get_verb_of_the_day(entries, *, language, date_str)` in `core/verb_loader.py` is the entry point (`app/routes/home.py`'s `home()` GET handler calls this, not `pick_verb_of_the_day()` directly). `pick_verb_of_the_day()` is the deterministic hash algorithm alone -- hashes `f"{language}|{date_str}"` with SHA-256, indexes into `entries` sorted by verb id (not the caller's rank order) modulo the entry count -- but that algorithm's stability guarantee breaks the moment the demand-driven generation pipeline adds a verb mid-day, since that changes `len(entries)` and therefore the index (found+fixed 2026-09-16, issue #40: the original design assumed catalog size only changed via infrequent admin action, which stopped being true once autogen started running on every unauthenticated search-miss). `get_verb_of_the_day()` persists the day's first computed pick to a small `verb_of_the_day/{language}_{date}` Firestore doc (`{language, date, verb_id}`) via `doc_ref.create()` -- same idempotent-first-write-wins idiom as `core.analytics.session_tracker._create_session()` (an `AlreadyExists` race loser re-reads and defers to the winner) -- so every subsequent read for that (language, date), from any Cloud Run instance, returns the same stored verb_id regardless of later catalog-size changes or per-instance `_ENTRIES_CACHE` differences. This is a deliberate small addition to Firestore reads/writes (one extra doc per language per day) over the original "no new storage" design, traded for an actual stability guarantee instead of one that silently stopped holding. Wired into `app/routes/home.py`'s `home()` GET handler, computed once per request and wrapped in try/except (logs and falls back to no chip on failure). Rendered in `app/templates/home.html` as `<a class="votd-hero">` (CSS in `app/static/home.css`), linking to `/learn?language=...&verb_id=...&ui_language=...`. ## Conventions & Constraints

- No frontend frameworks -- vanilla JS only
- No second database -- Firestore is the single source of truth
- Do not commit `.env` or secrets
- **Never use `set_cookie()` for non-`__session` names** -- Firebase Hosting CDN strips all other cookies before forwarding to Cloud Run and before returning responses to the browser
- When adding a feature: does it conflict with the stateless/frictionless UX principle?
- Always read `Makefile` and `pytest.ini` before touching test config


- Use the **qa-engineer** agent for writing and maintaining tests

- **Firestore in tests (issue #8):** `tests/fake_firestore.py` (`FakeFirestore`/`FakeCollection`/`FakeDocRef`/`FakeSnapshot`/`FakeBatch`) is an in-memory fake covering the subset of the Firestore client API this codebase's write paths use -- `.create()` raises `AlreadyExists`, `.update()` raises `NotFound` on a missing doc, `.set(merge=True)` shallow-merges, `collection_group()` reports a real `.reference.path` (docs are stored flat, keyed by full slash-joined path, so path-parsing callers like `admin_feedback_service._read_practice_summary` work against it); `firestore.Increment` is resolved (added to the existing numeric field) on set/create/update, so counter tests can assert real totals; other sentinels are stored opaquely. **No unit test can reach the real project:** the autouse `_no_real_firestore` fixture in `tests/conftest.py` pre-seeds `core.storage.firestore_db._db` (the lazily-built client singleton behind `get_db()`) with a fresh per-test `FakeFirestore`, which covers every import style of `get_db` and keeps the "empty / not found" behavior tests used to get implicitly. It also resets `verb_loader._ENTRIES_CACHE` per test. This exists because `.env` points `GOOGLE_CLOUD_PROJECT` at the live project and dev machines have valid ADC, so a test that forgot to mock Firestore used to read and write live data (search tests once incremented real `verb_search_hits` counters), hidden by every writer's `except Exception`. `tests/e2e` is exempt on purpose (its in-process server reads the live project); tests that patch `get_db` themselves still win. Request the `fake_db` fixture to seed or inspect state (it returns the same per-test instance); `seed_spanish_verb(fake_db)` in `tests/conftest.py` puts one minimal verb in. Non-Firestore live services (Vertex/Gemini, Anthropic) are not guarded. Six older ad-hoc `_FakeDb`-style mocks remain scattered across the suite; they are not migrated. **Patching a name that other modules also import (issue #58):** a plain `monkeypatch.setattr("core.x.name", ...)` on the *defining* module silently stops applying the moment a consumer does a module-scope `from core.x import name`, and `assert_not_called()` then false-greens. Use `patch_everywhere(monkeypatch, "core.x.name", replacement)` from `tests/conftest.py` (identity-matches every loaded `app.*`/`core.*` module holding the same object and patches them all), or patch the *consuming* module's own name. `tests/test_patch_targets.py` fails with file:line and the holder modules if a test patches a defining-module name that others hold; the `get_db` sites are allowlisted there (the autouse guard already covers them; moving them off string patches is #58 step 3). Examples of state-assertion tests on the shared fake: `tests/test_admin_feedback_service.py`, `tests/test_session_tracker.py`.
